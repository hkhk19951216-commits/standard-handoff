# 严谨溯源（可选手册）

仅在用户要求严谨溯源、长周期项目、或进入审计档时读本册。默认导出不需要它。

## 什么时候值得多花这份力气

跨天 / 跨周的项目、多人接手、要做架构或数据格式决策、或用户明确说「把证据标清楚」。一次普通的换窗口继续，用主文件加模板就够。

## 逐条事实标可信度

每条关键事实后面可加一个标记，标记跟着证据走，**不跟着格式走**：把一条 `REPORTED` 抄进表格不会让它变成 `CONFIRMED`。

| 标记 | 含义 |
|---|---|
| `CONFIRMED` | 本次会话直接看过工件、当前命令输出或一手来源 |
| `REPORTED` | 只来自用户、旧交接、会话回顾、记忆或第三方转述；即使对方说「已验证」「已通过」也算这一类 |
| `INFERRED` | 推理得出的结论，必须写出依据 |
| `UNKNOWN` | 证据缺失。**不要为了叙事完整补空**，也不要猜一个看起来合理的值 |

时间戳、任务 ID、分支、commit、行号、测试结果拿不到就写 `unknown` 或只写日期，不编造精度。

## 四级事实状态（防「把原型当已实现」）

- `verified`：由当前代码、配置、测试、构建产物或运行环境直接证明。
- `documented-only`：只来自产品文档、设计稿、口头决策，实现未证明。
- `prototype-only`：仅交互原型、演示数据、视觉占位。
- `TBD`：未确认，必须写明决策者或验证方式。`TBD` 是合法状态，**不是待填占位符**。

另外区分「已实现 / 已测 / 已审 / 已部署」四件事，不要压成一个「完成」。`coverage: FULL` 只是导出方在声明的范围内没发现实质遗漏的主张，不是独立验证，更不是「完整对话或整棵项目树都被捕获了」。

## 引用，不复制

需求文档、计划、ADR、issue、commit、diff 已经在仓库或链接里，就只写路径或 URL 加一句说明。复制内容会制造第二份事实来源，改了一处忘另一处。唯一值得保留逐字引用的，是那些措辞一漂就会改变含义的原话。

## 脱敏清单（写之前过一遍）

密钥、访问令牌、API key、Cookie、密码、私钥块、Bearer 值、`.env` 里的真实值、个人身份信息、大段日志、隐藏推理。用全角括号写「（见环境变量 X）」这类占位，**不要用尖括号**，尖括号留给校验器判定未解决占位符。

## 易过期状态

分支与 commit、未提交改动、测试最后一条命令与结果、外部系统状态、日期、锁、运行中进程——每条带观测时间，或明确写 `unknown`。旧交接与记忆只当线索，当前一手证据优先。

## 边界

本册只提升「可核查性」，不提供来源真实性、署名、审批、授权或语义连续性的证明。结构校验 `PASS` 不代表事实为真，也不代表下一步可以安全执行。
